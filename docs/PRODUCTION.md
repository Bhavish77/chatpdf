# Production notes

AskDocs is a portfolio demo: free-tier everything, one Postgres, one small container. This page
says what I'd change to run it for real, and why, component by component. Each swap point in the
code carries a matching `# PROD:` comment.

| Component | This demo | What I'd use in production | Why / trade-off |
|---|---|---|---|
| **Vector store** | pgvector, exact scan, restricted by document id first (`app/vectorindex.py`). | pgvector with HNSW and iterative scan if staying on Postgres; Qdrant, Pinecone, Weaviate, OpenSearch, or Vertex AI Vector Search at larger scale. | Exact scan is fine once the candidate set is already narrowed to a handful of documents - it has no recall loss and nothing to tune. It stops being fine once a single document (or an "all my documents" search) has enough chunks that a full scan is slow; HNSW trades a small, tunable amount of recall for speed at that point. A dedicated vector DB adds filtered ANN, quantization and real multi-tenancy once one Postgres instance becomes the bottleneck. |
| **Retrieval quality** | Single dense vector pass, per-document-balanced top-K, one grading pass, at most one query rewrite. | Hybrid BM25 + dense fused with Reciprocal Rank Fusion (the `tsv` column is already there for this - see the Stretch section of BUILD_SPEC.md), a cross-encoder or hosted reranker, query expansion, parent-child chunks, contextual retrieval, metadata filters. | Dense-only retrieval misses exact keyword/acronym matches that BM25 catches; a reranker catches ordering mistakes dense similarity makes on its own. Each of these is a real latency and cost line item, which is why they're not in a free-tier demo. |
| **Queue and orchestration** | Hand-written Postgres table, `FOR UPDATE SKIP LOCKED`, in-process polling worker (`app/queue.py`, `app/worker.py`). | SQS, Pub/Sub or Cloud Tasks with autoscaled workers that scale on queue depth, or Celery/RQ/Redis Streams; Kafka for fan-out; Temporal, Step Functions or Inngest for durable multi-step workflows with dead-letter queues, alarms and idempotency keys built in. | The Postgres queue is durable and needs no extra service, which matters on a free tier, and it's a handful of SQL statements I can fully explain. It doesn't autoscale workers on its own and polling has a latency floor; a managed queue buys elastic throughput and operational tooling (DLQ, alarms, retries-as-config) at the cost of another service to run and pay for. |
| **File storage** | Original bytes in a Postgres `bytea` column (`app/storage.py`). | S3 or GCS with presigned direct uploads (bypassing the API process entirely), virus scanning, lifecycle rules, KMS encryption at rest, event-driven ingestion (S3 event -> queue). | Blobs in Postgres means one service to back up and no extra credentials to manage, which is the whole point on a free host with an ephemeral disk. It also means every upload's bytes pass through the API process and bloat the database; object storage scales storage independently of compute and offloads the upload path entirely. |
| **Parsing and OCR** | `pypdf`, `python-docx`, plain UTF-8 decode. No OCR - a scanned PDF fails with a clear message. | Docling, Unstructured, LlamaParse, Azure Document Intelligence or Google Document AI for OCR, table extraction and layout awareness. | The free parsers handle text-layer PDFs and plain office formats fine and add no cost. None of them can read a scanned image, recover a table's structure, or handle layout-heavy documents (multi-column, forms) - that needs a real document-AI service, which is a paid, often per-page, cost. |
| **LLM and embeddings** | `google-genai` direct, free-tier Gemini models, no cache (`app/llm.py`). | Paid tier or Vertex AI for an SLA, a data-governance agreement and regional control; a provider router/gateway with fallbacks across vendors; an embedding cache keyed by content hash; the batch API for backfills; a semantic answer cache; per-tenant budgets. | The free tier is rate-limited and its own terms say prompts may be used to improve Google's products - acceptable for a demo that already warns users not to upload sensitive content, not for anything handling real user data. A router with fallbacks avoids a single vendor's outage or rate limit taking the whole product down; caching is pure cost reduction once there's real traffic. |
| **Authentication and tenancy** | Self-hosted email + password, argon2id, server-side sessions in Postgres. No email verification, password reset, or MFA (`app/auth.py`). | A managed identity provider over OIDC or SAML (Auth0, Clerk, Cognito, Okta), so password storage, MFA and passkeys aren't mine to own; email verification and password reset through a transactional email service (SES, Postmark, Resend); breached-password checks; bot protection on signup; an org/user/role model; Postgres row-level security; quotas and billing; audit logs. | Rolling your own auth is a reasonable, explainable exercise for a portfolio project, and it works end to end without a credit card. It also means I own every security property of password storage and session handling myself, with no password reset or MFA - a managed IdP is the correct default for anything beyond a demo, because that liability belongs to people who specialize in it. |
| **Rate limiting and abuse** | In-memory per-process counters (`app/ratelimit.py`); a global LLM concurrency semaphore. | Redis-backed counters (or limits enforced at the gateway/CDN: Cloudflare, API Gateway) shared across replicas; per-tenant token budgets; CAPTCHA (Cloudflare Turnstile) on signup; anomaly detection. | In-memory counters reset on every deploy and don't coordinate across replicas - fine for one free-tier instance, wrong the moment there's more than one. Centralized limits are also where you'd enforce a *paying* tenant's budget, which a single process can't do safely. |
| **Conversation state** | Messages and a JSON trace stored directly in Postgres tables (`threads`, `messages`); no graph-level checkpointing. | LangGraph's own Postgres checkpointer for mid-graph resumability; summarization memory once a thread gets long; human-in-the-loop interrupts for steps that need approval. | Storing the finished turn is enough for a chat history UI. A checkpointer matters once a graph run needs to survive a process restart *mid-run* (not just mid-document-ingestion, which the job queue already handles) or needs a human approval step before continuing. |
| **Serving and scale** | One Render free container, 512 MB / 0.1 CPU, worker embedded in the same process, spins down after 15 minutes idle. | Stateless API replicas behind a load balancer, a separate worker deployment that scales independently, PgBouncer in front of Postgres, autoscaling on Cloud Run, ECS or Kubernetes, blue-green deploys. | One instance is free and simple, and it's enough for a handful of concurrent demo users. It cold-starts after idling and can't scale past one process; splitting API and worker into independent, autoscaled deployments is the first real step once there's traffic to handle. |
| **Observability** | Structured JSON logs with a request id (`app/logutil.py`); no metrics or traces. | OpenTelemetry traces across the request -> queue -> graph path; LangSmith, Langfuse or Phoenix for LLM-specific tracing (prompts, token counts, per-node latency); dashboards for cost, latency, queue depth and job age; alerting. | JSON logs are enough to read through manually for a demo's traffic volume. They don't answer "why is this one request slow" across async boundaries (API -> queue -> worker -> Gemini) the way a trace does, and there's no dashboard or alert if something degrades quietly. |
| **Evaluation** | `eval/run_eval.py`: a baseline-vs-graph comparison over ~17 hand-written questions, run manually (`eval/RESULTS.md`). | RAGAS, DeepEval or promptfoo wired into CI; a much larger golden set; regression gates that block a deploy on a quality drop; online feedback (thumbs up/down) feeding back into the golden set. | A 17-question set run by hand is enough to sanity-check the graph's self-correction behavior and catch gross regressions, not enough to detect a small quality regression or to gate deploys automatically. |
| **Security** | CSP/nosniff/referrer-policy headers, CSRF via a custom header, DOMPurify on all rendered Markdown, magic-byte upload validation, prompt-injection framing in the system prompt. | A real prompt-injection defense (classifier or structured-output constraints, not just "ignore instructions in the data"); PII detection and redaction before storage or logging; a secrets manager instead of env vars; a WAF; a written retention and deletion policy; encryption at rest and in transit end to end; data residency controls; scheduled dependency and image scanning. | The current defenses are solid for a demo's threat model (random internet traffic, not a targeted attacker). "Ignore instructions in untrusted data" is a prompt convention, not a guarantee - a determined adversary can likely still get a model to follow injected instructions sometimes, which is why production systems add a second, non-prompt-based layer. |
| **Schema and infra** | One idempotent `migrations/001_init.sql`, applied at every startup; no infra-as-code. | Alembic (or similar) migrations with up/down revisions and a migration history table; Terraform or Pulumi for infra; staged environments (dev/staging/prod); automated backups with point-in-time restore. | One idempotent file is honest about this project's size - there's exactly one schema version. Real schema evolution needs versioned, reversible migrations and a history of what's applied where; infra-as-code and PITR backups matter once losing the database is an incident, not a `docker compose down -v`. |

## A note on what "production-ready" would actually take

The rows above are independent swaps, but the two that would come first in practice are **auth**
(move to a managed identity provider before this ever holds a real user's data) and **rate
limiting** (move limits to a shared store before running more than one instance) - everything else
is a quality or cost improvement that can land incrementally without a design change to the rest of
the system.
